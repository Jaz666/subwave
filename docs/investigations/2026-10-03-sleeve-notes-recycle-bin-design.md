# Sleeve Notes Recycle Bin proposal — 3 October 2026

The owner wants research to do only essential factual cleanup, followed by a generic DJ review. Claims rejected by that review go to the moderation page, which becomes a Recycle Bin. A live DJ can explicitly reject an approved spark; three distinct DJ rejections also move it to the bin. Pending bin entries expire 30 days after entry if the owner does not intervene. Show oldest entries first.

## Decision flow

1. **Research:** retain the source-linked Full and reject only unusable receipts or unsupported factual claims. Category, topic and Short defects are repair work, not a verdict on the Full. True duplicates are dropped. Wikipedia credit-only claims remain excluded.
2. **Generic DJ review:** decide `ready`, `matching-release-or-track-only`, or `bin` with a short reason. The review judges listener value and presentation using the Full and source; it does not override factual support. A conditional claim needs an explicit release or track identity before it can be offered.
3. **Link selection:** offer only an eligible claim for the current track. The live DJ may use it or explicitly reject it for an intrinsic quality reason. A timing omission, shorter link, persona style choice, failed generation or context mismatch is not a rejection. Count at most one explicit quality rejection per claim per distinct link opportunity. On the third, disable the claim and move a snapshot to the bin.
4. **Recycle Bin:** list pending items by `bin_entered_at ASC, id ASC`, with source, Full, reason, origin (`generic DJ` or `live DJ`), rejection count and an expiry date. Owner approval or editing returns a claim to service and clears its DJ rejection count; owner deletion removes/suppresses it. An item awaiting owner action cannot be selected for a link.
5. **Expiry:** purge unreviewed bin entries at 30 days from `bin_entered_at`, not from source retrieval, claim creation or last display. Use a background cleanup job and a timestamp predicate so restarts do not extend the clock. Existing historical pending items start their own 30-day clock at migration, avoiding immediate deletion. Preserve a minimal suppression fingerprint without claim prose so an unchanged source does not regenerate an expired claim. Purge dependent review/history rows or move aggregate counts to a separate non-claim record before deleting claim rows, because current use and history tables reference claim IDs.

## Existing code to change

`researcher.ts` currently applies category, shape, topic, bare-milestone and editorial vetoes before or alongside Full support and requires a valid Short for Wikipedia retention. `research-worker.ts` stores every rejection in the current moderation table. `llm-researcher.ts` has no generic DJ review result. `link-selection.ts` and the link writer record offered and aired claims, but the link model returns spoken text only: absence from that text cannot safely be counted as a rejection. `moderation.ts` sorts pending items newest first, and the current schema has no bin-entry timestamp, expiry or DJ rejection counter. The existing `sleeve_claim_uses`, `sleeve_claim_history` and `sleeve_moderation_history` foreign keys constrain physical deletion.

Implementation was added in the working tree after this design record. It has not been deployed, and the live database has not been reset. The active research calls are `sleeveNotesResearch` and `sleeveNotesCheck`; the live DJ rejection count advances only when a link carrying an explicit quality verdict is confirmed on air.

Subsequent owner refinements: the link writer may record a `SPARK_NOT_NOW` context pass without affecting the rejection count, and the four structured Genius sample/cover relationship types stay eligible as sparks but are exempt from automatic Recycle Bin moves while their airtime behaviour is evaluated. Bare Genius credits remain stored for Connections but are excluded from spark selection.
